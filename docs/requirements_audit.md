## State and transition rules in the current design

The database call lifecycle uses `INITIATED`, `COMPLETED`, `FAILED`, and telephony outcome values such as `NO_ANSWER` where applicable. The awaiting-confirmation state is represented by `call.pending_payment_date` plus the latest persisted agent confirmation question; it is not a separate `call_status` enum value.

1. `INITIATED` with no pending date → a customer turn may produce a date-specific agent question; the proposed date is persisted as `pending_payment_date` only when the generated question contains a recognized confirmation phrase/date.
2. Pending date + matching date/amount question + explicit affirmative response → backend validates against the call's linked EMI and stored agent message, commits the promise, clears pending date, and completes the call.
3. Pending date + rejection, ambiguity, conflicting date/amount, or absent proposal → no commitment is saved; the old pending proposal is cleared and the call remains open unless the scenario closes it.
4. Wrong number, unavailable/callback, refusal, or unable-to-pay may close the call according to the extraction and response rules; no commitment is inferred from the label alone.
5. A subsequent message to a completed call is rejected. A retry through the commitment endpoint for the same already-confirmed date is idempotent; a different date is rejected.
